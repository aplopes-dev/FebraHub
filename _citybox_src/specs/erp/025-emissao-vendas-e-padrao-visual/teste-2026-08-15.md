toda — que é o comportamento correto quando há dois formulários que salvam separado.

## P1 ⚠️ — a autenticação foi corrigida; a emissão parou um passo depois

**O que melhorou:** o `HttpFiscalApiClient` deixou de usar token estático/`dev-admin` e passou a
obter token de serviço por `client_credentials` (client **`fiscal-m2m`**), como recomendado. E a
separação de erros que pedi foi implementada — os logs agora distinguem `[FiscalAuth]` de
`[FiscalBusiness]`, o que é exatamente o que me permitiu localizar o problema abaixo.

**O que ainda falha:**

```
POST /v1/nfse-issuances → 422
"Não foi possível resolver o Emitente fiscal da organização."
```

A mensagem vem de `http-fiscal-api-client.ts:114`, no ramo `if (!response.ok)` da busca
`GET /v1/companies?cnpj=`. Ou seja: **o token foi obtido** (senão cairia no erro de `[FiscalAuth]`),
a requisição chegou à fiscal-api, e a fiscal-api **recusou**.

### 🔴 Causa-raiz: `FISCAL_API_URL` sem o sufixo `/api` no `.env.example`

**Não é autenticação.** Reproduzi no Swagger a chamada exata que o erp-api faz, com o **mesmo
client (`fiscal-m2m`) e o mesmo realm (`citybox-erp`)** — token válido, `azp` conferido:

```
GET /fiscal/api/v1/companies?cnpj=36698609000123&active=true
200  → { id: "070566ad-…", cnpj: "36698609000123", defaultEnvironment: "HOMOLOGATION" }
```

O client, o realm e a permissão estão corretos. O que está errado é a **URL base**.

O cliente monta `${FISCAL_API_URL}/v1/companies`. Testei as variações:

| `FISCAL_API_URL` | URL final | Resultado |
| --- | --- | --- |
| `…/fiscal/api` | `/fiscal/api/v1/companies` | ✅ **200** |
| `…/api` | `/api/v1/companies` | ❌ **502** |
| `…/fiscal/api/v1` | `…/v1/v1/companies` | ❌ **404** |

E o repositório está **internamente inconsistente**:

```
apps/erp/api/.env.example:53      FISCAL_API_URL=http://127.0.0.1:3116        ← SEM /api
http-fiscal-api-client.ts:11      DEFAULT_FISCAL_API_URL = '…:3116/api'       ← COM /api
apps/erp/api/AGENTS.md:430        (default `http://127.0.0.1:3116/api`)       ← COM /api
```

O default do código está certo; o `.env.example` está errado. E como definir a variável
**sobrescreve** o default correto, qualquer deploy que tenha usado o `.env.example` como modelo
ficou com a base sem `/api` — cada chamada vira `…:3116/v1/companies`, que devolve 404, cai no
ramo `if (!response.ok)` e produz exatamente a mensagem observada.

**Correção:** ajustar `FISCAL_API_URL` no deploy da erp-api para incluir `/api` (externo:
`https://api.aplopes.com/fiscal/api`; interno: `http://fiscal-api:3116/api`) **e** corrigir o
`.env.example`, senão o próximo ambiente repete o erro.

**Confirmação em 1 minuto:** o log da erp-api registra
`[FiscalBusiness] Busca de Emitente por CNPJ recusada (HTTP <status>)`. Se for **404**, é a URL
(esta hipótese). Se for **401/403**, aí sim é token/permissão.

> ⚠️ O secret do `fiscal-m2m` foi colado no chat na sessão anterior — **rotacione-o** de qualquer
